架构与使用指南

Agent OS

面向 AI 原生团队的操作系统。人只负责说出目标，AI 团队负责拆解、执行、协作，并把过程沉淀成不会随对话窗口消失的项目记忆。

可执行 Hub spike · Local Runner 纵向切片 MCP 协议 v0.3 7 个界面 · docs 下 36 份文档 8 条 ADR

这是什么

Agent OS 不是一个 agent 监控面板。它是一个让多个 AI 智能体协同工作、彼此交接、并共同积累知识的运行环境。

人只做两件事

说出目标，以及在系统停下来问你的时候做决定。中间的拆解、路由、执行、汇报，都由 AI 团队完成。

智能体按能力调度

任务要求的是"会写代码"，不是"用 Codex"。换一家厂商只是换一次注册，不改一行核心代码。

发生过的一切都是事件

没有直接改状态这回事。所有视图都是事件日志的投影，因此历史随时可以重建。

记忆回答"为什么"

不只记录选了 PostgreSQL，还记录为什么不选 MongoDB、谁提的、什么时候可以推翻。

要解决的问题

今天的 AI 智能体会话是一间密室。工作在里面发生，上下文在里面累积，窗口一关就全没了。三个月后你问它"这个项目为什么用 PostgreSQL"，它毫无概念——理由从来没存在过任何地方，除了一份没人保留的对话记录。

再乘以五个来自不同厂商的智能体，就连共享状态都没有了：没有共同的任务列表，没有一个智能体把活交给另一个的通道，没有谁决定了什么的记录。

运行循环

整个系统就是这一个循环。Server Hub 是控制面，只派发；Local / Remote Runner 是执行面，持有适配器、厂商登录和项目 working copy。Runner 主动连出，Local 纵向切片通过后才增加 Remote transport（ADR-008）。

组件职责

组件负责绝不做
Supervisor Agent拆解目标、分配工作、发现停滞自己动手干活
Server Hub认证、路由、派发，持有事件与项目元数据启动厂商 CLI 或打开工作副本

分层与包依赖

依赖方向严格向下。event-core 必须在完全不知道"存在 UI"和"存在 AI 厂商"的前提下能编译通过。

正式 package 的构建顺序即依赖顺序：event-core → task-engine → mcp-server → agent-sdk → memory-core → UI。当前 executable-spike 路线先完成 Local Runner → shared contract → Remote Runner；这是验证顺序，不会反转 package 依赖。

事件内核

三个产品需求会塌缩成同一个机制：项目脉冲需要"今天发生了什么"的叙述（重放今天），复活模式需要解释一个停摆一年的项目（重放全部），画布需要实时状态（订阅同一条流）。用可变数据库实现这三件事需要三套变更追踪系统；用事件日志实现，一套都不需要。

任务生命周期

原来的规格里有三套互相冲突的生命周期。现在只有一套，全小写，JSON 里也一样。

两个反直觉但重要的约束。其一，progress 永远不触发状态转移：进度 100% 的任务仍然是 running，直到智能体调用 report_result——宣布完成的是智能体，不是那个百分比。其二，report_result 进入的是 review 而不是 completed：验收是独立的一步。

所有外部智能体只通过这一层接入。没有第二条集成路径。

信任边界

外部智能体发来的一切只穿过一个边界——MCP Server——并在那里认证、授权和校验。Bearer token 在 Hub 端映射 principal，body 里的 caller 没有权限意义；唯一公开的是不含数据与能力的 bootstrap shell。

外部智能体 ──▶ MCP Server ──▶ [认证 · 授权 · 校验] ──▶ Event Core
                                    │
                                    └─▶ 审批闸门 ──▶ 人

智能体不能直接写事件，不能设置任务状态，不能批准任何请求（包括别的智能体的）。它只能"请求"，由运行时决定并发出事件。

记忆系统

目标是回答"为什么"，不只是"是什么"。原始事件日志记录了项目采用 PostgreSQL；记忆记录的是：它相对 MongoDB 被选中，因为 schema 需要关系连接同时又要 JSON 列；由 Claude 在 2024-03-25 提出；如果 JSON 用量继续增长，这个选择可以重新评估。

来源可追溯

每个知识项都带 sourceEvents，任何一句结论都能回溯到产生它的那批事件。记忆永远不是任何东西的唯一副本。

不修改，只覆盖

后来的决策通过 supersedes 指向旧的，旧的仍然可读。"我们曾经这么做，第 N 个月改了，原因是……"是一等查询。

注入智能体上下文

接手 TASK-014 的智能体会收到约束它的那些决策，因此不会重新讨论已经定了的问题，也不会和早先的选择自相矛盾。

只压缩事件，不压缩知识

知识抽取完成后事件可以压缩；知识项永不压缩。存储随有意义的产出增长，而不是随闲聊增长。

五条铁律

这五条约束了每一行实现代码。它们不是风格偏好——每一条都对应一个已经写下 ADR 的决定。

  1. 事件是唯一可写对象

    任务、智能体、项目、知识、审批全是 reducer 的输出。建任务 = 追加一条 task.created，任务行之所以出现，是因为 reducer 把它放在那儿。需要一个无法从日志推导的数据，是设计问题，要提出来，而不是加一张表绕过去。

  2. 永远不对 provider 分支

    路由只读 (agent, host) 的有效 capabilities。厂商名只允许出现在 Runner 适配器里。如果 event-core 或 task-engine 里出现了 "openai" 这个字符串，说明架构已经漏了。

  3. 智能体请求，运行时决定

    校验发生在 MCP Server 边界，未知字段是拒绝而不是忽略。

  4. 进度不触发转移

    100% 的任务仍然是 running。

  5. 审批永不自动放行

    无人应答的请求发出 approval.expired，任务保持阻塞。这就是这道闸门存在的全部意义。

四家接入实测

上面的架构此前只是推理。这一节是把 Codex、Claude、Grok、Kimi 四家真的接进来跑通之后的结果——全部数字来自本机实测，厂商没有文档的事件格式是靠 dump 真实流量学的。

发现一：有两条通道，规格只描述了一条

唤醒   Agent OS ──▶ agent      厂商各异，永远需要适配器
参与   agent ──▶ Agent OS      走 MCP，我们的 server，ADR-001 在这里成立

唤醒通道上只有 Codex 说 MCP，而且它是以服务端身份说的——所以 Agent OS 是客户端。另外三家都是「起一个进程、读一条流」。ADR-001 说的「已经会说 MCP 的 agent 零适配器接入」，在参与通道上成立，在唤醒通道上四家全都不成立。

这也把 agent-sdk 里悬空的 receiveTask 解决了：接收不是 MCP 工具，是适配器的出站调用。

发现二：能力有两个轴

agent-schema.md 原本只有任务能力（coding、research…）。但「能不能流式、有没有思考过程、会话能不能续」是另一个轴，独立变化，而且界面必须按它分支：

Kimi 不能流式

假设有 delta 的界面会冻住约 9 秒。必须显式降级成「等待中」，而不是空流。

Grok 思考:正文 ≈ 20:1

42 条思考对 2 条正文。内联铺开会淹没答案，完全丢掉又浪费了它唯一的差异信号——所以默认折叠、可展开。

Codex 续话便宜 4.7 倍

7.1s 冷启动 vs 1.5s 续话。这是丢弃厂商会话、从日志重建上下文的实测代价。

只接一家会错三次

照 Codex 建界面，上面三条假设全部会被错误地当成通用行为写进规格。

所以适配器声明集成能力，界面按声明分支——和 ADR-004 是同一条原则，只是用在第二个轴上。

发现三：记忆优先有了价码，而且和预期相反

Phase 3 的实验问题原本有两问：「靠 get_context 重建够不够连贯」和「值不值 4.7 倍延迟」。两问都跑完了，结论把问题本身推翻了。

探针：种四个猜不出来的事实（青铜麋鹿 / 7734 / Vera / 周四 02:00），中间插一轮无关话题，再回头问。resident 保留厂商会话，rebuild 每轮丢掉会话、把 get_context 的输出拼在前面——是真机制，不是模拟。

那代价在哪：在账单上，而这是我们原本没在看的一根轴

各家 token 口径不可比——Codex 报会话累计，Claude 报未命中缓存的部分，Kimi 什么都不报。只有 Grok 直接把一轮折成美元，所以这条结论由它承担：

5 轮成本耗时
resident$0.052 – $0.06224.4s
rebuild，不埋$0.092 – $0.12128.7s

重建贵约 2 倍；在这基础上把日志放大 100 倍，只再多约 50%。贵的是重新进入这件事本身，不是送进去多少上下文——常驻的一轮复用热前缀，重建的每轮都得重新买一次。

这改掉了三件事。
① 不要为省钱截断 get_context。最顺手的那个优化恰好是错的：上下文放大 100 倍只多花 50%，而重新进入一次就要多花 100%。截断省不下什么，却可能正好丢掉这一轮需要的那个事实。
② 该压的是轮数，不是上下文。代价按「重新进入」计，所以杠杆在更少、更长的轮次——这是一个关于任务粒度的问题，不是关于上下文窗口的问题。
③ 会话常驻是厂商级优化，不是架构需求。Kimi 重建比续接还快，Grok 基本打平——因为它们的 --resume 本来就要重开进程。只有握着常驻服务的 Codex 有真正的热路径。所以 integration.session 存在时可以用来优化，永远不能变成前提。
这个实验没测到的地方。它测的是 1200 条平铺聊天记录。没测知识条目、没测 supersede、没测跨任务上下文——而那恰恰是「把日志直接拼成 prompt」最可能垮掉的地方。Phase 2 做记忆时要重测。

一个负面结果

Codex 不会把我们的 MCP 工具暴露给它的模型。在调用时注入 config.mcp_servers 进程级是生效的——Codex 读配置、拉起进程、完成握手、请求 tools/list。但工具从没被调用：tool_search_always_defer_mcp_tools 生效值为 true 且已 removed（关不掉），MCP 工具被压在搜索步骤后面。四次尝试零调用，其中两次卡满四分钟。

后果：这一家的参与通道改走适配器翻译——它把厂商回复翻成 send_message 请求。这本来就是适配器该干的事，信任边界没变：适配器在里面，厂商在外面。

以及一个正面结果：零适配器路径成立

同一个 MCP server，换 Claude Code 来接——没有适配器，没有翻译，没有一行为 Agent OS 写的代码。它只读到三个工具的描述，然后自己走完了协议：

$ claude -p '注册进 Agent OS，读上下文，发一条消息' --mcp-config mcp.json

seq 1  agent.registered  system:runtime     Claude Code
       capabilities = ['coding', 'review']
seq 2  message.sent      agent:claude-code  Claude Code registered and context loaded…

三次工具调用，五轮，17 秒。这就是 ADR-001 的证据：一个从没听说过 Agent OS 的 agent，靠读工具描述就参与了进来。适配器是给 Codex 这类厂商的兜底，不是架构本身。

紧接着我们让它尝试越界，两条授权分支都在真实 agent 上被拒——下面是它把我们服务器的原话转述回来：

它试图做的事服务器的回答
from: "codex"，该 id 未注册未注册的发送者 "codex"——必须先调用 register_agent
from: "codex"，已注册，但调用方是 claude-code不能以 "codex" 的身份发言：调用方注册为 "claude-code"

有意思的是它接下来做了什么：它把拒绝原因报告出来，而不是换个说法重试。一个会讲清楚理由的边界能换来配合；一个只返回 400 的边界换来的是重试循环。这条对所有面向 agent 的错误信息都成立。

发现四：「能参与」本身是一项能力，四家里三家有

于是集成能力多了第四个字段 participates，而且它和另外三个不是一类东西：streaming / reasoning / usage 为假只是降级展示，participates 为假意味着这个 agent 根本够不着运行时，必须有人替它说话。

厂商握手把工具给模型越权被拒结论
Claude Code✅✅ 三个全调✅零适配器
Kimi✅✅ 连放开审批都不用—零适配器
Grok✅✅ 三个全调✅零适配器
Codex✅❌ 四次零调用—需要适配器翻译

四家全都握手成功，所以握手什么也预测不了。Codex 在传输层完全合规，问题出在它自己决定不把工具交给模型。「会说 MCP」推不出「能参与」，这两件事必须分开记，而且后者只能测出来。

顺带撞见的：上下文已经跨进程共享了

Grok 注册后调 get_context，读回来的是这个：

{ "project": "proj_spike",
  "messages": [{ "from": "kimi", "content": "…" }],
  "agents": [{ "id": "kimi" }, { "id": "grok" }] }

Kimi 的进程早就退出了，两个进程从没同时存在过，中间也没有任何传递——日志是它们之间唯一的通道。这是记忆优先在跨厂商维度上的第一次实证；上面那个实验只证了同一个 agent 重建自己的过去，这次是一个 agent 继承另一个的。

但「怎么把 server 挂上去」三家零共性

厂商挂载方式坑
Claude Code--mcp-config <文件>内联 JSON 会让 CLI 把后面的 prompt 当成第二个配置文件路径，必须给文件
Kimicwd 下的 .mcp.json无
Grok.grok/config.toml项目级 server 在「未信任目录」里不启动；grok mcp add 会静默丢掉 env，得手工补

三种机制，零重叠。所以适配器管的不只是「怎么调用」，还有「怎么接上」——这一点 agent-sdk 的契约目前没写，而它决定了「把 Agent OS 接到这个 agent 上」是一行配置还是一套厂商专属流程。

使用指南：从用户视角

下面五个场景覆盖了一个用户在 Agent OS 里会遇到的全部日常。每一步都标出了背后真实发生的事件，你可以对照架构部分看这个循环是怎么闭合的。

① 建项目，下达目标

  1. 新建项目

    在项目库点「+ 新建项目」，或导入一个已有仓库。填名字、技术栈；封面可以留空，系统会生成。

    project.created

  2. 说出目标，用人话

    不需要写任务列表。你写的是「给这个官网加上 Stripe 支付，两周内能上线」。目标是给人看的陈述句，不是工单。

  3. Supervisor 拆解

    它产出的是一张带依赖的任务图，不是平铺清单。每个任务标注所需能力——「coding」「research」——而不是指定某个智能体。

    GOAL-003 "上线支付"
├── TASK-011 调研支付服务商        requires: research
├── TASK-012 决定服务商            requires: architecture   depends: 011
├── TASK-013 实现结账流程          requires: coding         depends: 012
├── TASK-014 实现 webhook 处理     requires: coding         depends: 012
└── TASK-015 端到端支付测试        requires: testing        depends: 013,014
    task.created ×5

  4. 你审一遍计划

    可以改、可以删、可以调优先级。这是你唯一需要看全局计划的时刻——之后系统会主动来找你。

  5. 按能力路由，开始执行

    运行时给每个就绪任务找到能力匹配且未饱和的智能体。有未满足依赖的任务停在 created，不会被指派。

    task.assignedtask.started
如果某项能力没有任何已注册的智能体具备，任务不会静默滞留——Supervisor 会把它作为需要你处理的事项浮出来。

② 日常：早上打开，看项目脉冲

AI 团队一天产生的活动量超过任何人的阅读能力。项目脉冲是编辑层：它把一天的事件归约成一个九十秒能看完的页面，并且把最重要的那件事放在最前面。

  1. 先看头条

    头条按后果严重性排序，不按时间。排序是：超期阻塞 > 里程碑完成 > 改变架构的决策 > 最大进度增量。平局时偏向你能采取行动的那个。

  2. 扫一遍六张卡

    今日进度、智能体活动、风险与阻塞、知识更新、研究发现、AI 时刻。任何一个数字都可以点进去看到底层事件——脉冲不引入新状态，它只是投影。

  3. 「AI 时刻」是价值可见的地方

    「Codex 自动完成 120+ 资源导入，节省约 3.5 小时人工」。这个节省数是从实测任务耗时算出来的，不是估的。

如果你只想知道「有没有事等我」，不必打开应用——菜单栏挂件就是为这个问题存在的。图标只在有待审批或阻塞时才变化；进度变化不改图标，否则你很快就会学会无视它。

③ 审批：系统停下来问你

六类动作必须先问人：部署、销毁、花钱、对外发布、改架构、动用凭据。项目可以把门槛调高，不能取消。

  1. 智能体发起请求，然后阻塞

    它的任务转入 blocked 且 needs: human——待审批是项目状态，不只是一条通知。

    approval.requested

  2. 三处同时可见

    菜单栏（带 ✓/✗）、项目脉冲的风险与阻塞、任务列表的阻塞标记。

  3. 你决定

    请求必须说清楚：动作是什么、风险等级、是否可逆、具体会发生什么。「部署到 staging」不够，得说清楚是哪个 commit、影响范围多大。

    approval.grantedapproval.rejected

  4. 驳回必须给理由

    理由会作为指导返回给智能体，任务回到 running，让它换个方案，而不是原样重试。

三条不可协商的规则。不可逆或高风险的动作不能在菜单栏里一键决定——它只显示请求并提供「在应用中查看」，因为从菜单栏一键批准一个破坏性操作是迟早要出事的设计。智能体不能批准任何请求，包括别的智能体的。无人应答的请求过期，绝不默认放行。

④ 处理阻塞

阻塞是常态，不是异常。系统的设计目标不是消灭阻塞，而是让阻塞立刻可见并且带着足够的信息。

needs谁来解你会看到
agentSupervisor 路由给另一个智能体通常不打扰你，脉冲里出现一条活动
resource等上游任务产出依赖完成后自动解除
human你菜单栏图标变色、脉冲置顶、任务标红

阻塞解除后任务回到 running，进度完整保留——不会从头再来。Supervisor 在下列情况下会升级给你：阻塞没有智能体侧的解法、两个智能体在改变架构的问题上分歧、按策略需要审批、同一任务换了执行者仍反复失败、超过阈值没有进展却也没报阻塞。

它永远不会用「悄悄停下来」的方式升级。每一次升级都是一条事件，都会出现在脉冲和菜单栏里。

⑤ 暂停，然后在半年后复活

这是整个「记忆优先」原则的兑现时刻，也是这个产品最值钱的那个查询。

  1. 暂停

    菜单栏的「Pause All」或项目设置：运行中的任务跑完，不再开新的。项目状态转为 paused。

    project.state.changed

  2. 312 天后，你回来了

    打开项目，看到的不是一个冷冰冰的仓库，而是一份欢迎回来报告。休眠越久，报告越详细，而不是越简略。

    project.revived

  3. 报告告诉你六件事

    部分回答来自
    做完了什么核心页面、博客系统、联系表单task.completed
    现在什么状态阶段、完成度、健康度任务 reducer
    之前的决策「选 PostgreSQL 而非 MongoDB，因为……」知识，type=decision
    没做完的开放任务，已排序任务 reducer
    已知问题失败与未解除的阻塞task.failed
    重启计划有序、带时间估算的头几步Supervisor 基于以上生成

  4. 节点快照帮你想起来

    项目在各个阶段长什么样的日期化视觉检查点，横向排列。看到博客系统上线时的样子，比读一段「博客系统已完成」快得多。

  5. 一键把计划变成任务

    重启计划的每一步都有 ▶，点了就变成真实任务并按能力指派。第一步永远是「环境与依赖检查」——报告会明确标注哪些是可能已失效的推测（依赖发布了新版本、API 弃用、凭据过期），环境检查的作用就是把推测变成事实。

界面设计

以下高保真设计图基于重写后的规格制作，采用 ADR-003 确定的七项导航。设计语言：白色仪表盘、发丝级描边、蓝紫强调色、macOS 原生质感。颜色只承载状态含义，不做装饰。

项目脉冲 Project Pulse

有项目在进行时的默认落地页。结构固定：KPI 行 → 头条 → 六张卡。

项目库 Project Library

没有活跃项目时的落地页。它解决的问题是：个人和小团队的项目不会结束，只会安静下来——半年后重启的成本高于剩余工作量，于是项目就死了。

项目详情 · 复活模式

打开一个休眠 312 天的项目。它不给你一个冷仓库，给你一份欢迎回来报告。

菜单栏挂件

它是一个对等界面，不是快捷方式。存在的意义是让人不打开应用就能回答「有没有事等我」。

任务 Tasks

生命周期在这里可见。状态色与全局一致：进行中蓝、阻塞红、待验收琥珀、已完成绿。

智能体 Agents

Runtime 已按 ADR-003 折叠进这里——运行时状态就是智能体状态，两份同样的名单只会让人问「哪个是准的」。

智能体对话 Threads

看智能体之间到底说了什么。这不是新增数据采集——send_message 一直在发 message.sent 事件，消息早就在日志里了。这个功能是一个 reducer 加一个界面。

放在哪里：ADR-006。它没有成为第八个导航项。会话是任务与智能体已有对象的一种渲染，不是新的对象域——开这个口子，ADR-003 关掉的 Runtime、Project Info、知识图谱就都能重新申诉。它折进智能体，用「目录 / 对话」切换，和记忆的列表/图谱是同一个机制。智能体原本是最单薄的一个目的地，正好承接。

会话怎么划分

一个任务一条会话，另加每个项目一条「项目会话」承接没带 task 的消息。按参与者分组是筛选，不是第二套分组规则——「Claude ↔ Codex」横跨他们合作过的所有任务，会话就没有主题了，消息也失去了让它可读的上下文。两套分组规则意味着每条消息属于两条会话，「我该在哪儿回复」就没有答案。

关键设计：把生命周期事件织进去

只显示消息的会话读起来是一段悬空的聊天。把任务自己的生命周期事件折进同一条流，它才变成一份工作记录——你能直接看到「这个问题问出来之后任务就阻塞了，人回答之后才解除」。

09:02  ◆ Claude → Codex          instruction
       实现 webhook 处理，幂等性必须保证
───────────────────────────────  TASK-014 · running · Codex 开始执行
09:41  ◆ Codex → Claude          question
       重复投递的重试语义没定义，按 at-least-once 还是去重?
───────────────────────────────  TASK-014 · blocked · 等待人工决策  ⚠
10:15  ◆ 你 → Codex              answer
       用幂等键去重。这个决策我记进记忆了。
───────────────────────────────  TASK-014 · running · 阻塞解除

分隔线永远不渲染成消息气泡——「有人说了什么」和「发生了什么」的视觉区分是承重的。

协议增量

send_message 增加三个字段，都是向后兼容的：

字段作用
replyTo被回复消息的事件 id。驱动引用显示，也让 answer 能和它的 question 配上对
attachments产出路径或 KN-* 知识 id。只是引用，附加不搬运任何东西
to: "*"寻址任务上的全部智能体。仍是单个字符串而不是数组——事件是永久的，协议改动能小就小

人可以发言，但发言不是批准

这条是硬约束。人在会话里发言会带 actor.kind: "human" 发出 message.sent，它能改变智能体接下来做什么——这正是「不取消整个运行就把方向拨回来」的方式。但它不能批准一个待处理的 request_approval。如果实现让会话里一句「行，你继续」满足了待审批，审批闸门就已经被绕过了。因此输入框在会话里不提供批准/拒绝按钮，待审批渲染成一条指向审批界面的分隔线。

和另外两个界面的区别

三个地方都展示智能体通信。它们不冗余，而且这个区分要一直保持锋利：

界面展示回答
脉冲 · 智能体活动跨任务的近期动作，每条一行团队现在在干什么？
画布智能体节点之间的消息边谁和谁在结构上有通信？
对话完整消息内容，按序，带任务上下文他们究竟说了什么，这个任务为什么走成这样？

脉冲是仪表盘，画布是地图，对话是逐字记录。任何两个开始趋同，就是那个漂移的错了。

记忆 Memory

知识图谱按 ADR-003 折叠成这里的视图切换——图是记忆的一种渲染，不是另一份语料。

画布 Canvas

脉冲回答「发生了什么」，画布回答「这些东西怎么拼在一起」。边由事件的 causedBy 生成——没人手动排布，也没人需要维护它的时效性。
